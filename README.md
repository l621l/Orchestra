# Orchestra

Экспериментальный консольный помощник для программирования на Python. Директор общается с пользователем, исследует и меняет проект, запускает настроенные проверки и делегирует исследования или реализацию работникам. Запросы идут через OpenAI-совместимый Chat Completions API; провайдер и модель выбираются отдельно для каждой роли.

В профиле `project` работники могут **редактировать и проверять код в отдельных Git worktree**. Директор просматривает их diff и явно переносит выбранные изменения в свой workspace, после чего проверяет объединённый результат и коммитит. Для исследований есть отдельный режим только чтения. Полноценная долговременная память пока не реализована.

Для схемы **«два независимых варианта → директор выбирает один → следующая итерация от победителя»** используй профиль `comparison`. В нём директор не имеет прямых инструментов записи файлов.

## Установка

Нужен Python 3.11+ (проект проверялся на Python 3.13). Git необходим для Git-инструментов и `apply_patch`; чтение, создание файлов, замена текста и проверки работают и без Git-репозитория.

Открой терминал в папке Orchestra. В Windows:

```powershell
py -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
```

В примерах ниже используется именно Python виртуального окружения — активация окружения не обязательна. Если зависимости уже установлены в выбранный Python, можно использовать `py orchestra.py ...`.

## Подключение моделей

Создай `config.local.json` рядом с `orchestra.py`. Если файл уже настроен, оставь его: повторная настройка не нужна.

```json
{
  "providers": {
    "mimo": {
      "api_key": "YOUR_API_KEY",
      "base_url": "YOUR_PROVIDER_BASE_URL"
    }
  },
  "roles": {
    "director": {"provider": "mimo", "model": "mimo-v2.6-pro"},
    "worker": {"provider": "mimo", "model": "mimo-v2.6-flash"}
  }
}
```

Подставь ключ и совместимый API-адрес из кабинета провайдера; названия моделей должны быть доступны твоему аккаунту. `mimo` — локальное имя записи, на которое ссылаются роли. Можно добавить другого провайдера и назначить его одной из ролей.

Ключи хранятся только в локальном конфиге. Он уже включён в `.gitignore`; не добавляй его в коммиты принудительно. SDK `openai` здесь используется как клиент протокола и сам по себе не означает отправку запросов в OpenAI.

## Запуск и параметры

Из папки Orchestra:

```powershell
.\.venv\Scripts\python.exe orchestra.py --workspace "C:\Projects\MyProject"
```

`--workspace` — папка проекта, **над которым работает агент**, а не папка установки Orchestra. Переданная папка должна существовать. Указывай корень репозитория, если нужны Git-инструменты. Запуск может менять файлы по твоему заданию: это не режим только для чтения.

| Параметр | Назначение | По умолчанию |
| --- | --- | --- |
| `--workspace PATH` | Корень доступных агенту файлов | `workspace/` рядом с `orchestra.py`; создаётся автоматически |
| `--profile NAME` | Профиль: `default`, `project` или `comparison` | `default` |
| `--settings PATH` | Другой файл общих настроек | `settings.json` рядом с `orchestra.py` |
| `-h`, `--help` | Показать справку и выйти | — |

Пути с пробелами заключай в кавычки. Относительные пути в аргументах считаются от текущей папки терминала. `--settings` меняет только общие настройки: `config.local.json`, `prompts.json` и `pricing.json` по-прежнему читаются рядом с программой.

После старта вводи задания в `You (exit to quit):`. Для выхода введи `exit`. Параметры запуска передаются **до начала диалога**, а не в сообщении модели. После изменения конфигов перезапусти программу.

## Разработка проекта по ТЗ

1. Подготовь отдельную папку проекта; Git-репозиторий необязателен, но удобен для контроля изменений.
2. Положи полное ТЗ в `whattodo.md`. Дай требованиям стабильные номера, например `R01`, `R02`.
3. Запусти профиль `project`:

```powershell
.\.venv\Scripts\python.exe orchestra.py --workspace "C:\Projects\TaskLedger" --profile project
```

4. Введи задание:

```text
Прочитай whattodo.md полностью и реализуй описанный проект.
Веди REQUIREMENTS.md: для каждого требования указывай реализацию,
проверки и оставшиеся пробелы. Запускай тесты и исправляй ошибки.
Не изменяй исходное ТЗ. В конце перечисли выполненное и невыполненное.
```

Имя `whattodo.md` не специальное: укажи другой файл в сообщении, если нужно. Программа не загружает ТЗ автоматически; промпт предписывает директору прочитать указанный файл инструментами. `REQUIREMENTS.md` также ведёт модель, а не автоматический оценщик.

Промпт задаёт поступательный порядок: минимальный запускаемый каркас и интерфейсы ближайшего этапа → конкретные задания работникам на реализацию/ревью → небольшие законченные возможности, перенос и проверки → сверка всего ТЗ. Заглушки допускаются явно, но считаются невыполненными требованиями. Для существующего проекта каркас заново строить не требуется.

### Профили

| Настройка | `default` | `project` |
| --- | --- | --- |
| Режим | Небольшое изменение, ограниченное исследование | Работа по многочастному ТЗ |
| Общий бюджет API-вызовов | 16 | 60 |
| Максимум вызовов одного работника | 8 | 12 |
| Максимум делегирований директора | 2 | 2 |
| Редактирующие работники | Выключены | Включены, отдельные worktree |
| Срок одного задания пользователя | 600 секунд | 1800 секунд |
| Резерв на завершение | 90 секунд | 120 секунд |
| Чтение после начала правок | Ограничено фазой реализации | Чтение и поиск остаются доступны |
| Проверка | Компиляция Python | `unittest` из `tests/` |

Общий бюджет включает директора и работников. Один API-вызов — один запрос к модели, а не один вызов локального инструмента; для продолжения после результата инструмента обычно нужен новый API-запрос. Работнику директор может выделить меньше максимума. Бюджет обновляется для каждого нового сообщения пользователя, не для каждого работника.

Это экспериментальные настройки, а не гарантия завершения любого проекта за один запуск. На остатке бюджета профиль `project` закрывает новые делегирования и просит завершить текущую работу, проверить её и перечислить пробелы.

### Два варианта и выбор победителя

```powershell
py orchestra.py --workspace "C:\Projects\TaskLedger" --profile comparison
```

Этот профиль реализует последовательные раунды:

1. Директор определяет небольшой этап и вызывает `start_comparison_round`. Программа создаёт ровно двух работников А/Б с одинаковым заданием от одного принятого коммита. Они пишут код независимо в своих worktree.
2. Директор ждёт обоих и просматривает оба доступных diff через `review_task_changes`.
3. `promote_candidate` выбирает **один вариант целиком**: переносит его patch, запускает все настроенные проверки основной копии и создаёт локальный коммит. Основная рабочая ветка — текущая ветка директора, не обязательно ветка с именем `main`.
4. Следующая пара начинается от этого принятого коммита. Старые worktree сохраняются для сравнения; сбрасывать их не требуется.

Если оба варианта не подходят, `reject_comparison_round` закрывает раунд, сохраняя прежнюю базу. Директор уточняет задание для следующей пары. Смешивание реализаций в этом режиме не предоставляется.

При провале проверки или коммита принятие отклоняется и программа пытается отменить только собственный перенос. Если файлы/HEAD изменились во время операции и откат может затронуть чужие изменения, она сохраняет состояние и явно сообщает, что требуется разбор. Оба исходных результата работников остаются в логах/worktree.

Перед стартом нужен Git-репозиторий с начальным коммитом, текущей веткой и чистыми доступными файлами/индексом. Исходное ТЗ удобно сохранить первым коммитом. Посторонние незакоммиченные изменения нужно заранее сохранить или разобрать; директор не будет молча включать их в выбранный вариант.

У директора недоступны `create_file`, `replace_text`, `apply_patch`, прямой `create_commit` и обходной `apply_task_changes`. Он читает, оценивает, запускает раунды и принимает результат. Каркас, тесты и `REQUIREMENTS.md` пишут работники. Отдельные исследовательские задания разрешены вне активного раунда.

Создание дополнительных веток в этом профиле по умолчанию выключено: принятие идёт в текущую ветку директора. Для отдельного эксперимента выбери нужную ветку перед запуском.

Начальные бюджеты `comparison`: 60 общих API-вызовов, до 12 на работника, 30 минут на сообщение пользователя. `execution.max_comparison_rounds` ограничивает число раундов за сообщение (сейчас 3); общий бюджет может закончиться раньше. Размер выделения для обоих работников выбирает директор одинаковым. Одновременно активен только один раунд с двумя реализациями.

Выделенные работникам вызовы сразу вычитаются из свободного бюджета директора. Когда в проектном режиме остаётся резерв на завершение, новые задания закрываются, а программа сама ждёт уже запущенных работников до срока финализации, не расходуя API-вызовы на опрос. Достигнутый резерв сам по себе не отменяет работников; реальный срок финализации по-прежнему ограничивает ожидание и оставляет время директору на итог.

Основные правила работы находятся в `prompts.json`. Подключаемого загрузчика skills пока нет: отдельный `SKILL.md` автоматически не читается. Успешное выполнение и проверки одного этапа не доказывают завершение всего ТЗ; покрытие нужно сверять с реальными файлами, тестами и документацией.

Настройки профиля — `profiles.comparison`. Стратегия задаётся `execution.development_strategy: "comparison"`, права — `roles.director.allow_editing: false` и `roles.worker.allow_editing: true`. Обычный `project` сохраняет стратегию `direct` с редактированием директором. Для сравнения результатов запускай разные профили на одинаковой исходной версии проекта.

## Где менять настройки

| Файл | Содержимое |
| --- | --- |
| `config.local.json` | Ключи, адреса провайдеров, модели для ролей |
| `settings.json` | Бюджеты, тайм-ауты, генерация, проверки, профили, разрешения Git |
| `prompts.json` | Инструкции директора, работника и завершения ответа |
| `pricing.json` | Тарифы для оценки стоимости; не актуализируются автоматически |

Основные разделы `settings.json`:

- `api`: тайм-аут ожидания данных, общий срок отдельного запроса и число повторов.
- `generation`: лимиты исследовательского ответа и отчёта, `temperature`, `top_p`. Лимит ответа действует на отдельный API-запрос, а не на всё задание; рассуждения могут занимать часть выходного бюджета.
- `execution`: общий бюджет вызовов и времени, резервы завершения, лимиты исследования, чтений и повторных ошибок редактирования.
- `roles`: количество делегирований, `director.allow_editing` и `worker.allow_editing` — права прямого редактирования.
- `tool_limits`: тайм-ауты Git и проверок, параллелизм локальных инструментов.
- `checks`: разрешённые команды проверок.
- `git`: режим коммитов и разрешение создавать новые ветки.
- `profiles`: переопределения базовых настроек. `default` означает базовые значения, `project` — базовые значения плюс `profiles.project`.

Настройки вложенных разделов объединяются, но `checks` в профиле **заменяет весь список проверок**. Неизвестные ключи в переопределениях отклоняются. Для отдельного эксперимента можно скопировать весь `settings.json` и запустить:

```powershell
.\.venv\Scripts\python.exe orchestra.py --workspace "C:\Projects\TaskLedger" --settings "settings.experiment.json" --profile project
```

Не все технические ограничения вынесены в конфиг: ограничения безопасных путей, размера файлов и формата инструментов остаются частью их реализации.

### Восстановление после обрезки ответа

Если запрос реализации исчерпал выходные токены, превысил тайм-аут или потерял соединение, следующая попытка идёт без отдельного thinking. Инструменты остаются доступны по правилам выбранного профиля; в `project` можно продолжать читать, искать и редактировать. Модель получает инструкцию сделать небольшой следующий шаг. После успешной правки восстановление сбрасывается и возвращаются обычные настройки генерации.

`execution.max_implementation_recoveries` задаёт число попыток восстановления между успешными правками (по умолчанию 1). Повторный сбой без правки завершает инструменты и запрашивает частичный отчёт вместо бесконечного повтора. Ответы с планом без реализации до первой правки учитываются в этом же пределе. Если и финальный запрос обрывается, программа формирует краткий отчёт сама, сохраняя доступный частичный текст и сведения о проверках. Обрезанные вызовы инструментов не исполняются.

Этот механизм ограничивает повторные сбои, но не гарантирует, что модель выполнит ТЗ. В логах есть события `implementation_recovery_scheduled`, `implementation_recovery_progress`, `implementation_recovery_exhausted` и `implementation_runtime_fallback`.

При обрезке или сбое потока полученный текст ответа и отдельные рассуждения провайдера полностью сохраняются в `drafts/<request_id>.json` внутри лога запуска. В продолжение директора и новые задания его работников автоматически включается выдержка последнего черновика родительской задачи: по умолчанию до 6000 символов текста, с началом и концом длинной записи. Это не смысловое резюме и не проверенный план; дополнительного API-запроса для него нет. Обёртка помечает заметки как непроверенные, а промпты требуют проверять их по текущим файлам и тестам.

Размер выдержки задаёт `execution.draft_context_characters` (0 отключает передачу, максимум 20000). Уже работающие работники не получают новые заметки задним числом. События `request_draft_saved` и `request_draft_handoff` показывают сохранение и передачу. Архив находится в логах Orchestra; файлы целевого проекта для этого не создаются.

## Проверки проекта

Модель вызывает `run_check` по имени. Команда берётся из `checks`, запускается в целевом workspace; произвольную команду или дополнительные аргументы модель передать не может.

Пример раздела:

```json
{
  "checks": {
    "syntax": ["{python}", "-m", "compileall", "-q", "."]
  }
}
```

`{python}` заменяется интерпретатором, которым запущена Orchestra. Зависимости проверяемого проекта должны быть доступны этому интерпретатору либо укажи путь к Python самого проекта. В базовой настройке `python_compile` сейчас указан абсолютный путь разработчика: на другом компьютере замени его на `{python}` или свой путь.

Профиль `project` рассчитан на Python: ищет `unittest`-тесты в `tests/` и считает отсутствие тестов ошибкой. Для другого стека настрой `checks` перед запуском. Компиляция проверяет синтаксис, а собственные тесты проекта не гарантируют выполнения всего ТЗ.

При нехватке вызовов программа может автоматически запустить настроенные проверки перед финальным ответом. Это не тратит API-вызов само по себе, но время выполнения входит в общий срок. Правки после проверки делают её результат устаревшим.

## Инструменты и Git

Работникам в режиме `research` доступны `list_files`, `read_file`, `search_text`, `search_regex`. В `implementation` добавляются создание и изменение файлов, настроенные проверки, чтение состояния/истории Git и `report_blocker` — всё в собственном worktree. Работники не коммитят, не создают ветки и не делегируют. Директор дополнительно управляет заданиями, принимает изменения и делает локальные коммиты.

### Работа с реализациями работников

В `delegate_task` директор выбирает `mode`: `research` (по умолчанию) или `implementation`. Последний требует `roles.worker.allow_editing: true`, Git-репозиторий и хотя бы один коммит. Пустую папку директор может развивать сам; перед первым редактирующим работником нужно сохранить начальный каркас коммитом. Исследования и локальное редактирование директора доступны без Git.

Для реализации создаётся отдельный detached worktree. Разрешённые текущие правки директора, включая незакоммиченные файлы, копируются в исходный снимок работника; основной индекс и ветка сохраняются. Для грязного снимка создаётся технический detached-коммит, не входящий в историю ветки директора; используется настроенная Git-идентичность.

После `wait_tasks` результат содержит workspace, изменённые пути, проверки и описание сохранённого patch-артефакта. `review_task_changes` возвращает diff и fingerprint; при обрезке можно запросить отдельный `path`. `apply_task_changes` переносит весь выбранный patch по fingerprint и должен вызываться отдельно. Проверки работника не заменяют проверки директором после переноса.

Если директор уже изменил затронутый файл, весь перенос отклоняется без частичной записи. Можно выбрать другую реализацию или согласовать изменения вручную инструментами. Независимые изменения разных работников допускают последовательный перенос. Автоматического слияния конфликтов нет. Перенос наследует ограничения `apply_patch`: создание/изменение текстовых файлов, до 30 файлов и 200000 символов diff; удаления, переименования, бинарные и режимные изменения требуют отдельного решения.

Worktree и JSON-артефакты сохраняются в `logs/<дата>/_workspaces/<запуск>/`; точные пути есть в событиях и результате задания. При отмене сохраняются доступные частичные правки. Инструменты просмотра/переноса обращаются к работникам текущего задания; после перезапуска остаются файлы и patch для ручного восстановления, автоматического возобновления пока нет. Не удаляй зарегистрированный checkout как обычный лог: для очистки сначала используй `git worktree remove PATH` после сохранения нужных изменений.

Worktree изолирует рабочие файлы, но не является системной песочницей для запускаемого кода. Зависимости и команды проверок должны быть доступны и в нём.

Git-инструменты: `git_status`, `git_diff`, `git_log`, `git_show`, `git_create_branch`, `prepare_commit`, `create_commit`. Создание файлов не требует Git. `apply_patch` принимает Git diff; для простых изменений существуют `create_file` и `replace_text`.

**В профиле `project` включён автономный локальный Git:** директор может создать новую рабочую ветку и коммитить законченные этапы без подтверждения. Перед автономным коммитом код требует успешного выполнения всех настроенных проверок после последних правок. Если проверок нет, этот барьер отсутствует; настрой релевантные `checks`. Директору предписано выбирать связанные изменения, сохранять чужую работу и описывать коммиты в финальном ответе.

Настройка в `settings.json` (для профиля — в `profiles.project.git`):

```json
{
  "git": {
    "commit_mode": "autonomous",
    "allow_branch_creation": true
  }
}
```

`commit_mode`: `manual` — одобрение точного сообщения и файлов по инструкции модели, `autonomous` — без подтверждения с проверками, `disabled` — инструмент коммита недоступен. В базовом профиле оставлен `manual`, создание веток выключено. Ручное подтверждение пока контролируется промптом, а не отдельным механизмом авторизации.

`git_create_branch` создаёт и выбирает только **новую** ветку от текущего HEAD; работает и до первого коммита. Файлы сохраняются. Переход к существующим веткам, слияние, push, amend и произвольная консоль не предоставляются. Код проверяет снимок файлов и индекс; уже существующие staged-изменения блокируют коммиты и создание веток. Перед первым запуском настрой Git-имя и почту обычным способом: Orchestra не придумывает их за тебя.

Для первого теста сохрани исходное ТЗ стартовым коммитом. Можно добавить к заданию: «Создай рабочую ветку, самостоятельно коммить законченные проверенные этапы и перечисли коммиты в отчёте».

Подробные контракты, ограничения и статусы проверок: [TOOLING.md](TOOLING.md).

## Прогресс, стоимость и логи

В терминале отображаются состояние каждого агента, текущая операция, время, количество полученных чанков и оценка расходов. Чанк — порция потока, не токен. Стоимость обновляется по полученному usage завершённых API-вызовов, а не по каждому поступившему токену.

В конце выводятся суммарные вызовы, входные/выходные токены, кэш, reasoning и оценка стоимости по каждому агенту и всему заданию. Кэшированные токены входят во входные, reasoning — в выходные: повторно прибавлять их не надо. Стоимость — оценка по `pricing.json`, не выписка провайдера.

Логи находятся рядом с Orchestra:

```text
logs/<дата>/turn_<идентификатор>__<тема>/
  events.json
  summary.json
  answer.md
```

- `events.json`: события, задачи, работа инструментов и эффективные настройки запуска (`runtime_configuration`).
- `summary.json`: итоговые состояния, изменения, проверки и сводка выполнения.
- `answer.md`: сохранённый итоговый ответ, если он был получен.

`partial` означает незавершённый результат; `completed` не заменяет независимую проверку требований. При ошибке или отмене уже записанные файлы не откатываются автоматически — проверь изменения перед продолжением.

Внутри задания история инструментов используется как контекст. После успешного завершения в истории диалога остаются вопрос и ответ вместо полной цепочки этого задания. Автоматической смысловой сводки длинного активного задания и восстановления диалога из логов после перезапуска пока нет.

## Тестирование самой Orchestra

Файлы `test_*.py` — автоматические проверки самой программы. Например, `test_commits.py` проверяет ветки, коммиты и сохранность индекса, `test_editing.py` — редактирование файлов, `test_runtime_profiles.py` — профили, `test_reliability.py` — восстановление после сбоев. Они нужны, чтобы новая правка не ломала уже работающие возможности.

Остальные Python-файлы — модули приложения: `orchestra.py` координирует работу; `tools.py` описывает файловые инструменты и делегирование; `git_tools.py` — редактирование, Git и проверки; `worker_workspaces.py` — снимки, worktree и перенос изменений; `execution_phase.py`, `verification.py`, `runtime_settings.py` — фазы, проверки и конфигурация; `workspace_policy.py`, `tool_contracts.py`, `tool_errors.py` — пути, аргументы и ошибки. Количество файлов не означает количество запущенных процессов или платных запросов.

Из папки Orchestra:

```powershell
.\.venv\Scripts\python.exe -B -m unittest discover -v
```

Это офлайн-тесты с подготовленными ответами моделей, временными папками и реальными локальными инструментами. Платных API-запросов они не делают. На Windows тест симлинков может быть пропущен, если ОС запрещает их создание.

## Частые проблемы

- **Импорт не найден:** установи `requirements.txt` в тот Python, которым запускаешь программу; в редакторе выбери тот же интерпретатор.
- **Git недоступен:** проверь установку Git и что `--workspace` указывает на корень репозитория. Остальные файловые операции могут работать без него.
- **Ноль тестов или проверка не запускается:** проверь папку `tests/`, команду в выбранном профиле и доступность её интерпретатора/зависимостей.
- **Нужны другие лимиты:** меняй `settings.json` либо передавай его копию через `--settings`, затем перезапускай программу.
- **Непонятно, почему работа закончилась:** открой `summary.json` и события текущего запуска; отличай лимит времени/вызовов от ограничения выходных токенов одного запроса.
