# Orchestra: tools-only

Одна модель работает непосредственно в выбранной папке. Внутреннее имя роли
`director` оставлено для совместимости с `config.local.json`; роли worker не нужны.
Нет делегирования, сравнения кандидатов, этапов, recovery и автоматической приёмки.

## Запуск

```powershell
python -B orchestra.py --workspace C:\path\to\project
```

Зависимости: `pip install -r requirements.txt`. Конфигурация провайдера и модели
берётся из существующего `config.local.json` (providers и roles.director).
Секреты в Git не добавляйте. Команды `--profile comparison` в этой ветке нет.

## Настройки и инструменты

- `tools.editing_enabled`: чтение + запись по умолчанию; false оставляет чтение и проверки.
- `tools.allow_git_mutations`: false по умолчанию; true разрешает создание новой
  ветки и локальных коммитов. Коммит требует успешных настроенных проверок после
  последней правки. Push, reset и merge не предоставляются.
- `checks`: имена и массивы аргументов доверенных локальных команд. `{python}`
  заменяется интерпретатором, которым запущена Orchestra. Команда выполняется
  из рабочей папки без оболочки. По умолчанию python_tests ищет unittest в tests/;
  для другого проекта измените эту команду. Пустой словарь отключает проверки.
  Проверки запускают код проекта: используйте доверенные рабочие папки.
- Бюджет: 16 API-вызовов на итерацию, последний оставлен для сводки.
  Одно введённое задание запускает пять итераций (до 80 обращений суммарно).
  `max_steps_per_agent` также равен 16; оба значения меняются в settings.json.
- Нет автоматического загрузчика skills. Инструкцию процесса пока можно менять
  в prompts.json или дать модели конкретный доступный файл для чтения.

Чтение: list_files, read_file, search_text, search_regex.
Правки: create_file, replace_text, apply_patch. Проверки: run_check.
В корне Git-репозитория дополнительно доступны status, diff, log, show и
prepare_commit. Создание файлов и точечные замены работают без Git-репозитория;
apply_patch требует установленный Git.

Вызовы исполняются последовательно в порядке ответа. Правки и проверки можно
объединять в одной пачке: они выполняются по порядку; создание ветки/коммита — отдельным вызовом.
Ошибки содержат конкретный код и объяснение, чтобы модель могла их исправить.
Проверки становятся устаревшими после новой правки. Непроверенные изменения
помечаются partial. completed означает завершение выполнения, а не доказательство
полного выполнения ТЗ. Логи сохраняют workspace_result с файлами и проверками.
Ошибка/отмена запроса НЕ откатывает уже выполненные изменения файлов.

## Офлайн-тесты

```powershell
python -B -m unittest discover -v
```

Тесты используют временные папки и подставные ответы модели, API не вызывают.

## Уточнения контрактов инструментов

- `read_file` возвращает `content_sha256` полного исходного файла, даже при чтении
  диапазона. Передайте его необязательным `expected_sha256` в `replace_text`, чтобы
  отклонить правку, если файл изменился после чтения. Хэш учитывает исходные байты,
  включая CRLF. Выход за конец файла даёт `invalid_range` с количеством строк.
- Длинные строки в поиске показываются вокруг совпадения, а не только с начала.
- Ответ после правки содержит до 2000 символов diff_preview и признак усечения;
  полный нужный участок можно прочитать существующим read_file/git_diff.
- Длинный вывод run_check сохраняет начало и конец, включая итоговую диагностику;
  omitted_bytes показывает размер пропуска. При таймауте доступен собранный вывод.
- git_log в новом репозитории сообщает об отсутствии коммитов без ошибки.

## Консоль и диагностика

Во время запуска видны таблица состояния и постоянная история действий:
имя инструмента, путь/проверка, результат и длительность. Неуспешные проверки
показывают код завершения и конец traceback. Ошибки инструментов показывают
конкретный код и объяснение. Для API выводятся безопасные причины (например,
HTTP 401/429, таймаут или исчерпанный лимит ответа), без тела ответа провайдера.
`summary.json` содержит error_message, events.json — события model_request_error,
результаты инструментов и вывод проверок. При исчерпании лимита генерации выполняется не более одного восстановления
(`execution.length_recovery_attempts`, 0 отключает). Оно расходует обычный бюджет
API, отбрасывает незавершённые команды и просит один небольшой шаг. Для моделей
MiMo после первого length все оставшиеся обращения текущего задания используют
thinking=disabled; новое пользовательское задание начинает с обычного режима.
Финальный принудительный отчёт также идёт без thinking. Для других моделей
параметр MiMo не отправляется. Повторный length или отсутствие бюджета дают
partial с сохранением имеющихся правок, без падения всего запроса. Другие ошибки
провайдера, включая content_filter, автоматически не повторяются.

## Пять последовательных итераций

Каждый ввод задания запускает iterations_per_task (по умолчанию 5) итераций.
У каждой до max_api_calls_per_turn (16) обращений, включая итоговую сводку:
всего максимум 80. Внутри итерации только первый запрос использует thinking=enabled,
последующие — disabled (параметр отправляется моделям MiMo). Принудительный
финальный отчёт всегда без thinking. При length выполняется только проверенный
законченный префикс команд; незавершённый хвост отбрасывается.
Следующая итерация получает системный промпт, исходное задание и только сводку
предыдущей с фактическими результатами проверок; история tool calls не переносится.
Рабочие файлы общие. Сводки сохраняются в iteration_1.json … iteration_5.json
в папке запуска. Сводка должна сохранять весь важный оставшийся backlog.
Пять итераций — максимум. По умолчанию stop_after_confirmation=true:
после done=true и успешных актуальных проверок следующая итерация проверяет
реализацию. Если она подтверждает готовность, проходит проверки и не меняет
файлы, цепочка завершается раньше. Правки или ошибки требуют нового подтверждения.
Заявление done=true в последней итерации без подтверждения остаётся partial.
Установите false для прежнего поведения с фиксированными пятью итерациями.
Ошибка API или отмена останавливает цепочку.

Названия run_check ограничены enum текущей конфигурации; точные массивы аргументов
показываются модели до первого действия. Промпт требует согласовать тесты с
этой командой, не повторять успешные проверки без изменений/новой гипотезы и
не подменять отсутствующие зависимости имитацией в коде продукта. Это инструкции
модели, а не автоматическое доказательство качества или запрет повторного запуска.

## Очистка контекста внутри итерации

execution.compact_tool_history=true включает архивирование старых объёмных
payload после достижения compaction_threshold_characters (по умолчанию 24000).
Последние два ответа модели сохраняются полностью; исходные сообщения старых
успешных инструментов записываются в context/ в папке лога до любых изменений.
Старое содержимое create_file/replace_text/apply_patch, чтений кода, поиска,
Git diff и успешных проверок заменяется короткими отметками. Пары вызов/результат,
пути, хэши и результаты проверок сохраняются. Ошибки, проваленные проверки,
пользовательские/системные инструкции и чтения Markdown сохраняются целиком.
Если архив нельзя записать, очистка пропускается. Для дальнейших правок модель
должна перечитать актуальный участок файла. Новых API-вызовов для очистки нет.
Размер контекста в логе теперь учитывает также аргументы инструментов и reasoning.
Это сокращает повторяющиеся данные, но не гарантирует конкретный процент экономии
токенов: определения инструментов, инструкции и недавние результаты остаются.

Обрезанные ответы сохраняются в *_truncated.json до обработки. Runtime проверяет
команды по порядку: ID, известный инструмент, законченный JSON и схему аргументов.
Законченные команды до первого некорректного вызова проходят обычную обработку
и ограничения доступа. При ошибке выполнения следующие команды восстановленной
части пропускаются с явным результатом. В историю попадают только выбранные вызовы
и парные tool results; незавершённые аргументы не подставляются как команды.
Git-мутации из обрезанного ответа не выполняются. Результаты видны в tool_finished,
output_limit_prefix_selected и output_limit_prefix_settled. Повторы не получают
нового бюджета: 100 вызовов и 20000 выходных токенов на запуск, до 4096 на ответ.
Модель получает точный контекст выполненных действий и просьбу сделать меньшую
законченную правку. При исчерпании бюджета законченные результаты сохраняются.

## Состояния и блокировки

Сводка содержит state: continue, ready_for_confirmation, needs_user или complete.
Старый формат done поддерживается. Готовность требует актуальных успешных
проверок и подтверждающей итерации без правок. needs_user останавливает цепочку
как partial: blocker обязан содержать action, reason, evidence — действие,
причину недоступности и наблюдаемую ошибку/границу полномочий. Это заявление
модели, а не автоматическое доказательство; пользователь видит свидетельство.
Отсутствие доступа модели к экрану не доказывает отсутствие дисплея. Настоящая
библиотека с dummy-дисплеем подходит для автоматической интеграции; ручная
визуальная оценка требуется отдельно только по явному условию задачи.

## Дополнительная экономия контекста

Результаты проверок передаются модели без строк unittest «... ok», с итогами;
ошибки сохраняют traceback и предупреждения. Полный вывод остаётся в events.json.
После актуальных успешных проверок большие исполненные правки архивируются,
не дожидаясь порога. Старые повторные чтения кода архивируются, когда есть
более новая успешная копия того же диапазона; два последних ответа защищены.
Для MiMo при thinking=disabled из передаваемой копии истории удаляются старые
reasoning_content. Для остальных моделей история reasoning не меняется.
События context_composition и request.context_characters показывают символы
инструкций, схем инструментов, правок, чтений, проверок и остальной истории.
Это измерение символов, не точный подсчёт токенов провайдера.

## Сопровождение интерфейсов при правках

Существующие create_file, replace_text и apply_patch принимают необязательное
interface_notes — до 8 записей вида:

```json
[{"path":"logic.py","symbol":"World.mode",
  "note":"Выбранный режим; new_game инициализирует его, рестарт сохраняет.",
  "related_paths":["main.py"]}]
```

Код применяется первым. После успеха инструмент автоматически обновляет объявления
PROJECT_MAP.md из исходников и сохраняет смысловые заметки в INTERFACE_NOTES.json.
Дополнительного API-обращения не требуется. Заметки описывают публичный контракт и
связи; локальные переменные карта не перечисляет. path должен входить в изменённые
этим вызовом файлы, symbol — существовать среди статически объявленных имён, все
related_paths — существовать. Неизвестное динамическое поле лучше описать заметкой
к его объявленному классу, а не выдавать его за найденное определение.

Заметка получает хэши основного и связанных файлов. После изменения любого из них
она показывается как STALE MODEL NOTE. Даже актуальная по хэшу заметка — утверждение
модели, а не доказательство правильности её смысла. Обновлять её нужно явно в
следующей относящейся к ней правке. Карта обновляется также перед запросами, поэтому
обнаруживает внешние изменения. В контекст передаётся не более 6000 символов
(execution.project_map_context_characters); последние изменённые файлы приоритетны.
Полная ограниченная карта доступна через read_file. В ней указаны исходные файлы,
номера строк, хэши и ограничения статического анализа Python.

Результат правки содержит interface_memory: обновление карты, количество сохранённых
и устаревших заметок, предупреждения. Сбой этой метаинформации не отменяет успешную
правку и не выдаётся за ошибку её применения. Существующие пользовательские файлы
с совпадающими именами без служебного маркера не перезаписываются. Генерируемые
файлы находятся в рабочем проекте; не редактируйте их вручную.
execution.project_map_enabled=false отключает сопровождение.

## Компактный режим по умолчанию

Карта в каждом запросе ограничена 2500 символами. Полная PROJECT_MAP.md доступна
через чтение по необходимости. Схемы инструментов используют короткие описания.
Git log/show доступны при tools.git_history_enabled=true; prepare_commit показывается
при allow_git_mutations=true. git_status и git_diff остаются доступны в репозитории.
Ответы после правок больше не дублируют diff; для просмотра есть read_file/git_diff.
Таймаут API сохраняет partial, список применённых файлов, результаты проверок и
сводку текущей итерации; цепочка останавливается без автоматических повторов.

## Снижение постоянного входа

Системные инструкции и формат итерации сокращены без изменения лимитов обращений.
Очистка старых payload начинается после 12000 символов (настройка порога сохранена),
минимальный архивируемый payload — 800 символов. Ошибки, неуспешные проверки,
Markdown-инструкции и последние два ответа остаются защищены. Метаданные успешной
правки для модели сокращены до статуса памяти и счётчиков заметок; полный результат
сохраняется в событиях инструмента. Реальную экономию и возможные повторные чтения
следует оценивать по следующему прогону; это не гарантия уменьшения стоимости.

## Текущий обычный режим: одна сессия

iterations_per_task=1 и stop_after_confirmation=false: одно введённое задание
вызывает одну рабочую сессию до 16 API-обращений, включая итоговую сводку.
Внутри неё история инструментов сохраняется и очищается по прежним правилам.
Новых автоматических сессий после неё нет; полный объём ТЗ может остаться partial.
Пять итераций и подтверждение по-прежнему доступны настройками для сравнения.

Команда «продолжи» (также continue/resume/дальше) подхватывает исходное задание,
последнюю краткую сводку и результаты проверок из logs/sessions для текущей
рабочей папки. Работает и после перезапуска. Полная история сообщений не переносится;
карта интерфейсов обновляется по текущим файлам, старые проверки — только сведения
о прошлом запуске, их актуальность нужно подтвердить. Новое обычное задание заменяет
сохранённую задачу. При повреждённом/отсутствующем состоянии API не вызывается:
нужно указать задание явно. Файлы проекта при продолжении не сбрасываются.
Это убирает ненужные автоматические итерации, но не устраняет повторную передачу
необходимого контекста на каждом API-обращении.

## Безопасный формат очистки истории

Завершённая успешная группа tool calls архивируется целиком: исходное сообщение
модели и все связанные результаты сохраняются точно, затем заменяются обычной
записью execution_record без исполняемых аргументов. Сохраняются пути, факты и
результаты проверок. Неполные группы, ошибки, проваленные проверки и чтения ТЗ
не архивируются. Аргументы оставшихся вызовов никогда не переписываются заглушками.
create_file, replace_text (новое содержимое) и добавляемые строки apply_patch
отклоняют известные служебные маркеры через archive_marker_not_source до записи.
Удалить старый маркер при восстановлении разрешено. Архивирование не меняет файлы
проекта; уже испорченные файлы требуют восстановления из настоящего исходника.

## Продолжение с уточнениями

«продолжи, сделай меню красивее» сохраняет исходную задачу и сводку, добавляя
текст после команды как отдельное пользовательское уточнение. Уточнения сохраняются
между запусками и передаются после старой сводки: они задают текущий фокус, не
отменяя оставшееся ТЗ. Обычный ввод без команды продолжения по-прежнему начинает
новую задачу. Для очевидной русской команды в английской раскладке консоль
предлагает расшифровку и ждёт подтверждения до API; автоматически текст не меняется.


## Эксперимент context-economy

Ветка `experiment/context-economy` сравнивается с контрольной точкой `05b870a`.
`execution.context_economy_enabled=true` включает группировку архивных записей
и очистку небольших проверенных правок. Последние две группы действий остаются
подробными. Уникальный актуальный код, ошибки и чтения Markdown сохраняются.
Старое чтение можно убрать при новом полном чтении того же пути либо при полном
покрытии диапазона с тем же SHA-256. Частичный фрагмент другой версии не заменяет
старое чтение. Оригинальные сообщения сохраняются в `logs/.../context/` до очистки.

Для сравнения отключить `context_economy_enabled`, оставив остальные настройки
одинаковыми. Оба прогона должны начинаться с одинакового состояния целевого
проекта и одинакового задания. Сравнивать результат игры, пропущенные требования,
число вызовов, input/cache/output и повторные чтения. Офлайн-тест сокращения
истории измеряет символы искусственного сценария, а не экономию токенов реального API.
Лимиты остаются: 100 вызовов, 20000 выходных токенов суммарно, 4096 на ответ.


Обрезание ответа (`finish_reason=length`) не завершает запуск, пока остаётся
бюджет вызовов и выхода. Незавершённые tool calls не выполняются; модель получает
инструкцию заново выдать меньшую законченную правку без thinking. Каждый повтор
учитывается в общем бюджете. Отдельный лимит в одну повторную попытку удалён;
на границе бюджета сохраняется частичный результат.
